# cuda-kernels-lab

**Question.** Can a hand-written CUDA kernel stack, from vector add to
a fused softmax kernel, be built and profiled against PyTorch on one
named GPU, with every number traceable to a recorded run?

**Headline.** No result yet: the project's own CUDA kernels are written
but have never been compiled or run, because the GPU node has no CUDA
toolkit. The one measured comparison is a baseline: on an RTX 5050
Laptop GPU, PyTorch's native fused softmax ran 3.9 times faster than
the same math as five separate PyTorch ops at 4096 by 1024 (0.0555 ms
against 0.2163 ms, one median per route from one session, no interval
recorded).

**Field.** ML and AI research (GPU kernels and profiling). **Job
family.** ML systems and inference engineering.

**Verdict.** Draft, not pre-registered. The code, tests and baselines
are real and CI passes on Python 3.11 and 3.12, but the system under
study, the custom kernels, has never run, so Functional is not met; no
plan with hypotheses was locked before the results, so Proposed is not
met either. A confirmatory re-run under a newly locked PROPOSAL.md is
planned (portfolio standard, METHOD section 7).

Live dashboard: https://jesunahmadushno.github.io/cuda-kernels-lab/

## Reproduce

```text
python3 -m unittest discover -s tests -v
python3 level-1-learn/run_learn.py
python3 level-2-build/run_build.py
python3 level-3-deep/run_deep.py
python3 level-3-deep/analysis_deep.py
```

Python 3 standard library and g++ (C++17) only. The runners regenerate
results_learn.json and results_build.json byte for byte (CI checks
this) and recompute every stored GPU throughput within 1 percent. The
GPU measurements themselves (level-3-deep/profiler_bench.py) need the
fleet GPU node with torch and are not re-run in CI. The dashboard:
`cd site && npm ci && npm run build`.

## Layout

| Path | What it holds |
| --- | --- |
| PROPOSAL.md | Question, draft hypotheses for the re-run, scope, prior work, dossier, level specs (not locked) |
| REPORT.md | Background, method, results that ran, misses, threats, research review, v1.1 backlog |
| level-1-learn/ | Code: CPU reference kernels and the C++ bench tool; evidence: results_learn.json |
| level-2-build/ | Code: C++ tool, tests, ASan session, custom kernels.cu (unrun); evidence: results_build.json, results_torch_bench.json |
| level-3-deep/ | Code: profiler study, C++ atomics and move benchmarks, fused_softmax.cu (unrun); evidence: results_profiler.json, results_deep.json |
| tests/ | Python unit tests, C++ runner checks, the layout and no-grade test |
| docs/decisions/ | Records of hard-to-reverse choices |
| docs/index.md | Static summary page (legacy Pages source) |
| fanout/, PUBLICITY.md | Dated write-ups for readers (drafts) and the channel log |
| site/ | The live dashboard, built from the results files and write-ups |
| CHANGELOG.md, CITATION.cff, SECURITY.md, LICENSE | Release notes, citation, security policy, licence |

There is no separate src/, experiments/ or results/ folder: code and
its evidence live together in the three level folders, which the site,
the tests and the CI all read by path. results_profiler.json and
results_torch_bench.json are GPU-node captures, never edited.
results_learn.json and results_build.json are regenerated byte for
byte. results_deep.json is the record of one C++ run: re-running
run_deep.py rewrites its wall times for your machine, so a re-run is
not committed over it. REPORT.md maps every quoted number to its file.
